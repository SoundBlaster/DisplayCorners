# Абстрактный протокол адаптера harness

Контракт описывает смысл обмена между Display Corners и адаптером. Формат сообщений, доставку, запуск адаптеров и API клиентов определят при реализации. Пакет SpecPM не запускает адаптеры.

## Роли и идентичность

Harness владеет сессиями и их состоянием. Адаптер наблюдает доступные сессии одного источника и преобразует подтверждённые наблюдения в общий словарь. Display Corners показывает состояния и передаёт выбранному адаптеру запрос перехода.

Адаптер предоставляет стабильный идентификатор источника, имя harness, возможности обнаружения работы и ожидания пользователя и возможность перехода. Для каждой сессии он предоставляет идентификатор в пределах источника, название проекта и имя агента, если они доступны. Отсутствующие возможности и поля обозначаются явно.

Пара идентификаторов источника и сессии определяет адрес строки. У двух сессий одного проекта разные адреса. Адаптер не подставляет вместо отсутствующих данных сведения другой сессии. Область действия идентификатора и возможность восстановить его после перезапуска определяет конкретный адаптер.

## Наблюдения и актуальность

Общий словарь состояний содержит working, waiting_for_user и unknown. Waiting_for_user означает подтверждённый запрос разрешения или ответа. Working означает подтверждённую работу. Адаптер не выводит ни одно из них только из тишины или существования процесса. Для изменения состояния он сообщает адрес сессии и отметку, пригодную для определения порядка.

Потребитель получает снимок при подключении и повторном подключении. Адаптер указывает его полноту. При полном снимке отсутствие ранее известной записи означает, что она больше не наблюдается этим источником. Неполный снимок этого вывода не допускает. Изменения могут передаваться отдельными обновлениями или новым снимком. Механизм доставки определит распознавание повторов и устаревших обновлений. Старое обновление не отменяет более новое подтверждённое состояние.

Актуальность источника и наблюдений ограничена простыми таймаутами потребителя. Подтверждение связи само по себе не подтверждает актуальность состояния сессии. После истечения соответствующего таймаута данные считаются устаревшими. Устаревание не является событием завершения или ответом пользователя. При восстановлении связи запрашивается новый снимок. Интервалы, способ подтверждения длительной работы без событий и отображение устаревших данных определяются при реализации.

## Переход к сессии

Потребитель отправляет запрос с идентификаторами источника и сессии. Адаптер возвращает accepted, если запрос передан клиенту, opened только если фактический переход подтверждён, либо unsupported, unavailable или failed. Потребитель ограничивает ожидание результата таймаутом. Истечение таймаута означает неизвестный результат и не доказывает, что переход не произошёл.

Переход не отвечает на запрос разрешения. Если переход недоступен, строка сохраняет адрес и показывает, что перейти нельзя. Конкретный текст и способы восстановления определяются при реализации. Повторное нажатие может породить новый запрос. Поведение повторов и подтверждения в конкретном клиенте предстоит проверить.

## Пример проверки

1. Два адаптера сообщают разные сессии одного проекта. Одна работает, другая ожидает пользователя. Каждая строка адресована своему источнику и сессии.
2. При открытии строки упорядочены от старого изменения к новому, свежие внизу. Пока меню открыто, состояния существующих строк обновляются на месте, а новые сессии добавляются сверху с сохранением строки под указателем. При подтверждённом продолжении работы ожидание убирается.
3. Источник перестал подтверждать актуальность. По истечении таймаута прежнее ожидание не показывается как актуальное и не объявляется обработанным.
4. После восстановления полный снимок заменяет устаревшее представление источника. Неполный снимок не удаляет отсутствующие в нём записи как завершённые.
5. Запрос на переход в одну из двух сессий поступает только её адаптеру. Accepted не выдаётся за подтверждённое открытие. Неподдерживаемый переход и таймаут различимы для потребителя.

Контракт не утверждает, что клиенты уже предоставляют перечисленные сигналы или подтверждения. Это проверяется для каждого адаптера.
